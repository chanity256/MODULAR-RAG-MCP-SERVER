# 文档治理（docs-governance）

将一个项目的开发文档组织为**分层、有生命周期、有索引、可追溯谱系**的体系，核心目标是：编码前能快速找到权威依据，编码后能留下可追溯的设计决策，并且任一主题都能一眼看出"从哪来、现在在哪、留下了什么"。

## 1. 目录结构与两类文档

为项目建立如下 `docs/` 结构（已有 docs/ 的项目按此对照补齐）：

```
docs/
├── MOC.md          # 索引文档（Map of Content）+ 文档谱系表，docs/ 增删文档必须同步更新
├── backlog/        # 流转文档 · 候选提案：有想法但未立项排期（含 README.md 约定）
├── specs/          # 流转文档 · 开发中规格：已立项、正在执行（可暂空）
├── frozen/         # 流转文档 · 冻结存档：已收口规格 + 谱系存档（只读）
├── analysis/       # 常驻文档 · 架构分析、能力对照、核验记录：判断，不承诺交付
└── reference/      # 常驻文档 · 面向使用者的速查手册与路线图
```

docs/ 下的文档分两类，规则不同：

| 类别 | 目录 | 是否流转 | 与其他文档的关系 |
|------|------|----------|------------------|
| **流转文档** | backlog/ → specs/ → frozen/ | 是，**目录即状态**，同一文件 `git mv` 前进 | 每个主题同一时刻最多一份活跃（位于 backlog/ 或 specs/） |
| **常驻文档** | analysis/、reference/ | 否，原地维护、版本号递增 | 可派生 0..N 个提案；以链接作为提案的「起源」，自身不移动 |

判断一份文档该放哪：

- **backlog/**：尚未立项的想法与遗留事项台账。宁可放 backlog 也不放进 specs 占排期。
- **specs/**：已立项、正在执行或有明确排期的规格。
- **frozen/**：任务全部收口、不再新增或改动任务的规格（带编号），以及谱系存档（不带编号）。冻结后只读，是该模块契约、验收标准与测试语义的**权威来源**。
- **analysis/**：分析与判断（技术选型对比、演进方向、能力差距、功能核验）。"结论是不做"同样是有效产出，长期保留。
- **reference/**：面向使用者的文档（使用指南、路线图），与开发规格分离。路线图条目也可以派生提案。

> **项目特化优先**：本 skill 是默认母版；项目 `docs/MOC.md` 若写有特化的命名与流转规范，以项目规范为准。

## 2. 文档生命周期

```
 analysis/ ──┐  常驻：判断与核验，可派生 0..N 个提案（只链接，不移动）
 reference/ ─┤  常驻：路线图条目也可派生提案
             ▼  起源引用
 backlog/<kebab>_backlog.md
     │  立项：git mv + 改写（单文件晋升）
     ▼
 specs/<NAME>_SPEC.md
     │  任务全部收口：git mv + 分配编号
     ▼
 frozen/<NN>_<NAME>_SPEC_frozen.md
     │  遗留事项：新建台账（反向箭头，新文件）
     └──────▶ backlog/<topic>-followups_backlog.md
```

### 2.1 流转方式（谱系表「流转方式」列的固定词表）

| 流转方式 | 何时使用 | 怎么做 |
|----------|----------|--------|
| **单文件晋升**（默认） | 一个提案对应一个规格（1:1） | 立项时 `git mv backlog/x_backlog.md specs/X_SPEC.md`，**分两次提交**：先纯移动（保证 git 识别重命名），再按 §6 骨架改写。提案三问的答案并入规格第 1 章「决策依据」，不再保留单独副本；需要追溯原提案原文时看 git 历史。分析文档就地升级为规格也属此类 |
| **提案存档** | 多个提案合并进一个规格（N:1），或规格大幅推翻提案、原文需要作为对照保留 | 立项时把每个原提案 `git mv` 到 `frozen/<原名>_backlog_frozen.md`（提案自立项起只读），规格文件头写「决策依据：<链接>」；不参与编号 |
| **拆分移交** | 一个提案只有一部分被某规格承接（1:N） | 承接部分写进接收规格（含「承接自」链接）；原提案留在 backlog/，删去已移交的内容细节，在文件头留一行移交记录（移交了什么、去了哪个规格）；剩余部分若需实施，按单文件晋升 |
| **跳过提案** | 用户在会话中直接拍板、决策依据已完整 | 直接在 specs/ 建规格，在第 1 章写明起源与决策（如「未经 backlog 草案阶段，决策依据见第 1、2 章」） |
| **重开** | 冻结规格经**明确指令**追加阶段 | `git mv` 回 specs/，去掉编号与 `_frozen` 后缀；再次冻结时**恢复原编号**（编号属于该规格，不重新分配），冻结记录头追加新的一行 |
| **派生台账** | 冻结规格留下"不做 / 负结果 / 已知缺陷"等遗留事项 | 新建 `backlog/<topic>-followups_backlog.md`，**不在冻结文档中追加任务**；台账中某项要推进时，按单文件晋升另起提案或从台账拆分 |
| **止于分析** | 分析结论是"暂不做"或"保持现状" | 分析留在 analysis/，谱系表记一行，"提案/规格"列留空 |

### 2.2 常驻文档的规则

- analysis/ 与 reference/ **不进入** specs/。提案与规格在文件头用「起源：<链接>（章节）」引用它们。
- **通用型分析**（服务多个主题，或结论长期有效）原地维护：现状变化时递增版本号，并在版本引言写明更新依据（如「v0.3 按 SX 系列收口结果更新」）。
- **绑定型分析**（只服务一个规格：该规格的输入调研、或该规格某个任务的交付物）在该规格冻结时**随之冻结**：`git mv` 为 `frozen/<原名>_frozen.md`，不参与编号。例外：仍被活跃提案或台账当作依据的，保留在 analysis/，等依赖方收口后再冻结。
- 规格对分析文档的勘误写在规格里，并在分析文档文件头加一行「后续/勘误见 <规格链接>」，不改写分析正文。

### 2.3 命名与编号

| 状态 | 位置 | 命名 | 编号 |
|------|------|------|------|
| 候选提案 / 遗留台账 | backlog/ | `<kebab-case>_backlog.md` | 无 |
| 开发中规格 | specs/ | `<NAME>_SPEC.md`（SCREAMING） | 无（冻结时才分配） |
| 已冻结规格 / 台账 | frozen/ | `<NN>_<NAME>_frozen.md` | 有 |
| 谱系存档（提案） | frozen/ | `<kebab-case>_backlog_frozen.md` | 无 |
| 谱系存档（绑定型分析） | frozen/ | `<原名>_frozen.md` | 无 |

- 编号三纪律：
  1. **编号 = 冻结顺序**（近似实现顺序），不按立项顺序；冻结时取 frozen/ 现有最大编号 +1，永不复用、不插入（重开后再冻结沿用原编号）。
  2. 非系列台账（如验收缺口清单）同样参与编号。
  3. frozen/ 中**不带编号**的文件都是谱系存档，不参与编号。
- 新规格的任务编号**用新前缀**，避免与已冻结规格冲突。前缀取规格名关键词的**首字母缩写**：`WEBUI_CHAT` → `WC`、`INGESTION_ROBUSTNESS` → `IR`、`LOGGING` → `LG`、`SIRCHMUNK_EXTENSION` → `SX`；2–3 个大写字母，立项时核查与全部既有系列不冲突。
- 历史遗留命名（如 SCREAMING 的 backlog 文档）沿用原名加后缀，不回改；已发生的历史流转不按新规则回迁，只在谱系表如实记录。

### 2.4 冻结操作清单（移入 frozen/ 时必须执行）

1. **命名与编号**：`git mv` 到 frozen/ 并按 §2.3 命名。全仓引用（MOC、README、AGENTS.md、backlog/README、引用方文档、代码与测试中的路径）同步更新。
2. **冻结记录头**：在文档开头（标题行之后、正文版本引言之前）补一段冻结记录，必含两项：
   - **冻结时间**：文档移入 frozen/ 的日期（以 git 记录为准）。
   - **完成概要**：大致完成的流程与功能（已收口的任务系列、关键交付物，3–5 行以内）。
   - 有遗留事项时补一行「遗留：见 <台账链接>」。

   ```markdown
   > **📌 冻结记录**
   >
   > - 冻结时间：2026-10-06
   > - 完成概要：阶段 A–I 共 68 项任务全部收口（…关键交付物…）；验收缺口 G1–G3 关闭。
   > - 遗留：见 [backlog/xxx-followups_backlog.md](../backlog/xxx-followups_backlog.md)
   ```
3. **连带处理**：检查该规格的绑定型分析（§2.2）是否随之冻结；有遗留事项则建派生台账。
4. **MOC 同步**：条目随文档移动、按新文件名更新链接，说明中注明「已冻结」与任务系列状态；**更新文档谱系表对应行**（§4.2）；根目录 README 导航表同步；backlog/README「当前候选」表移除已离开 backlog/ 的文档。
5. **drift guard 校验**：运行文档链接/索引 drift guard 测试（断言全仓 markdown 相对链接零坏链、docs/ 下每个文档都登记进 MOC），替代人工 `rg` 残留检查；没有该测试的项目建议按先例补一个离线单测。

立项（backlog → specs）时同样执行第 1、4、5 步：单文件晋升或提案存档、MOC 分区条目移动、谱系表更新、backlog/README 移除条目。

## 3. 编码前必读纪律

在项目 AGENTS.md（或等效的 agent 指令文件）中写入如下纪律（模板见 [assets/AGENTS-SNIPPET.md](assets/AGENTS-SNIPPET.md)）：

1. 编写代码之前，先读 `docs/frozen/` 下的已冻结规格（主规格 + 相关扩展规格）。
2. 改动某模块前，先查对应 spec 中该模块的**契约、验收标准与既有测试语义**：既有测试的语义属于契约的一部分，不得因重构而悄然改变。
3. 其余文档按需选读，不要求预先通读；想知道某主题的来龙去脉，先查 MOC 的文档谱系表。
4. 在 docs/ 下增删、移动文档后，必须同步更新 MOC.md 对应条目与谱系表，以及根目录 README 的「开发文档」导航表。
5. **AGENTS.md 的规格条目是精选清单，默认只进不出**：仅在规格冻结且对某模块构成「编码前必读」契约时新增一行（活跃规格的发现走 MOC 与 auto-coder 的规格同步机制，不经 AGENTS.md）；任务进度与状态回填（开发中 / 已完成 / 已完成任务的实测数据）**不进 AGENTS.md**，只写 MOC 分区说明与根目录 README 导航表。原因：AGENTS.md 是 steering 文件，改动即触发付费 agent evals，高频状态回填会让每次规格流转都花一次真实模型费用。

## 4. MOC 索引纪律

MOC.md 是 docs/ 的唯一索引，由三部分组成（格式见 [assets/MOC-TEMPLATE.md](assets/MOC-TEMPLATE.md)）：**命名与流转规范**、**文档谱系表**、**分区索引**。

### 4.1 分区索引

- 每个分区（specs/frozen/analysis/backlog/reference）一个表格，每个文档条目包含：链接 + 一句话说明（注明任务系列与状态，如「S 系列，S0–S4 已交付收口」）。
- 文档移动时，条目**随文档一起移动并更新状态描述**，不删除历史说明。
- 根目录 README 的文档导航表与 MOC 保持一致，两边同步维护。

### 4.2 文档谱系表

记录文档之间的对应关系与流转方式，**一个主题（或任务系列）一行**：

| 列 | 内容 |
|----|------|
| 主题 / 系列 | 主题名 + 任务前缀（如「WebUI + Chat（WC）」） |
| 起源 | 常驻文档链接（含章节）或非文件来源的文字说明（如「会话内审计」）；无则写 `—` |
| 提案 | backlog/ 或 `*_backlog_frozen.md` 的链接；无则写 `—` |
| 规格 | specs/ 或 frozen/ 的链接 |
| 后续 | 派生台账、规格派生的分析、更新过的常驻文档 |
| 流转方式 | §2.1 词表中的一个或多个，按发生顺序用 `→` 连接（如「提案存档 → 派生台账」） |

- 每次流转事件（立项、冻结、拆分、重开、派生台账、止于分析）都要更新对应行，与分区索引同一次提交完成。
- 谱系表只记录**关系**，状态描述写在分区索引；两边状态冲突时以文件所在目录为准。
- 一个文档可以出现在多行（如一份分析派生了两个提案），一行也可以有多个起源。
- 表格单元格中的链接与分区索引一样受 drift guard 约束，零坏链。

## 5. Backlog 提案约定

backlog/README.md 定义提案约定（模板见 [assets/BACKLOG-README-TEMPLATE.md](assets/BACKLOG-README-TEMPLATE.md)）：

- 每个候选功能一个文档，命名 `kebab-case_backlog.md`（如 `graph-rag_backlog.md`）。**`_backlog` 后缀是固定要求**，与 frozen/ 的 `_frozen` 后缀对齐，一眼可辨文档所处生命周期。
- 提案文件头写「起源：<常驻文档或冻结规格链接>」，说明想法从哪来。
- 提案必须回答三个问题（对齐「决策原则」）：
  1. 它解决了哪个**已经观察到**的问题？
  2. 是否有更简单、改动更小的方案？
  3. 如何通过测试、指标或用户流程确认它确实有效？
- 三问答不全的，只以草案形式记录，不进入排期。
- 提案写成「规格」形态（含任务表）也仍然是提案，立项前不进 specs/。
- README 末尾维护「当前候选」表：**只列 backlog/ 目录下实际存在的文档** + 一句话说明（含任务系列与状态）。已立项、已冻结的历史谱系看 MOC 谱系表，不在 README 重复。

## 6. 规格文档格式

新规格对齐既有先例，骨架见 [assets/SPEC-TEMPLATE.md](assets/SPEC-TEMPLATE.md)，必备章节：

1. **文件头注释**：一句话说明规格定位、基线状态、与其他规格的关系。
2. **版本引言**：版本号、起源与决策依据（链接原提案存档或常驻文档；单文件晋升时写「由 <提案名> 晋升，原文见 git 历史」；跳过提案时写「决策依据见第 1、2 章」）、基线、日期。
3. **核心目标与范围**：In Scope 表（模块 / 名称 / 优先级 / 一句话目标；区分承诺任务与门控任务）+ Out of Scope（明确不做清单，与「做什么」同等重要）。
4. **技术选型与模块设计**：含运行架构图与选型理由（对比被否掉的方案）。
5. **测试方案**：离线确定性测试如何注入 fake，真实依赖冒烟如何门控（环境变量开关），以及**既有测试语义**清单（本规格不得破坏的既有测试口径）。
6. **任务排期与进度跟踪**：任务表（编号 / 任务 / 验收标准 / 状态），交付后回填状态备注。

推荐章节（视规格性质追加）：

7. **验收清单**：可勾选的交付验收句子（功能行为 + 测试/typecheck/build 全绿 + 回写完成），与任务表互补——任务表管「做什么」，验收清单管「做完后整体长什么样」。
8. **实现合入后的回写清单**：本规格收口时要同步的架构文档（如 DEVELOPMENT_GUIDE §0 决策）、README、`.env.example` 等条目清单；数据层决策回写属 §0 级纪律，漏回写是治理事故。
9. **隐私注记**：规格涉及**个人内容落库**（新公开路由扩大暴露面）或**外发第三方服务**（LLM 等）时必备；写明暴露面变化、外发边界、默认关闭策略。

两条稳定性纪律：

- **章节编号只追加、不重排**：规格之间与规格内部常用章节号互引（如「LLM 模块见 NR §6」「隐私见该规格 §11」）。规格收口前新增内容时用追加章节/子节的方式，禁止为对齐模板重排既有章节号——否则跨规格引用全部断裂。规格的「目录」块负责说明本章编号与模板骨架的映射。
- **既有规格先例项目的对齐策略**：项目 MOC 声明的特化规范优先于本模板（母版原则）。为已有规格先例的项目写新规格时，**不重写先例**：沿用其章节编号风格，在文件头补齐模板必备件（文件头注释、版本引言四要素、结论速览、In/Out of Scope、架构图、带验收标准列的任务表），并在目录块标注必备章节 → 实际章节号的映射；缺的必备件作为子节插入对应章节，不新开顶层章节。

## 7. 新项目落地步骤

1. 确认项目已有 docs/ 目录；没有则按 §1 创建五个子目录。
2. 从 assets/ 复制模板：`MOC-TEMPLATE.md` → `docs/MOC.md`；`BACKLOG-README-TEMPLATE.md` → `docs/backlog/README.md`。
3. 已有文档按 §1 分类：收口的规格移入 `frozen/`（按 §2.4 清单命名、补冻结记录头），活跃规格放 `specs/`，判断类文档放 `analysis/`。
4. 将 [assets/AGENTS-SNIPPET.md](assets/AGENTS-SNIPPET.md) 的内容合并进项目 AGENTS.md（或等效文件），按项目实际改写文档路径与规格名。
