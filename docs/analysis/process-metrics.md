# 过程度量（process-metrics）

> 版本：1.0（2026-11-13）：第一份基线，只建立基线、不设目标值（规格 §3.5：目标值与告警阈值从 1.1 版起设）
>
> 起源：[AI_NATIVE_SDLC_SPEC.md](../specs/AI_NATIVE_SDLC_SPEC.md) §3.5（SD5）。性质：**通用型常驻分析**，原地维护、版本号递增，不随 SD 规格冻结。
>
> 数据来源：`python scripts/measure_process.py --rev <提交>`（离线只读，只读 git 历史；`--json` 输出机器可读结果）。口径由 `tests/unit/test_measure_process.py` 用临时 git 仓库锁定。

---

## 1. 指标口径

时长一律用**提交者时间**，单位小时。规格生命周期按**文件路径**从 git 历史推，不按提交信息匹配（立项提交的写法不统一）。

| # | 指标 | 类型 | 口径 |
|---|------|------|------|
| 1 | 立项 → 首个任务提交 | 领先 | 立项 = `docs/specs/<NAME>.md` 首次出现的提交；首个任务提交 = 拓扑序上立项之后第一个主题含 `[<系列><数字>` 的非合并提交（立项提交本身不算）。系列前缀取规格最新版本任务表中最多的 2–3 位大写编号前缀 |
| 2 | 立项 → 冻结 | 领先 | 冻结 = 文件从 `docs/specs/` 移入 `docs/frozen/` 的提交；重开后再冻结取最后一次；git 未识别为重命名时，退回「同一提交删 specs 文件、增同名 `_frozen` 文件」 |
| 3 | auto-coder 修复轮数分布 | 领先 | 提交信息中独占一行的 `Fix-Rounds: N`（SD5.2 埋点，含义见 auto-coder「Test & Auto-Fix」） |
| 4 | QA ⬜→✅ 周转 | 领先 | `QA_TEST_PROGRESS.md`（含 SD6.1 前的 `.github/skills/qa-tester/` 路径）各版本中，同一用例首次 ⬜ 到其后首次 ✅ 的时长；首次出现即 ✅ 的用例单独计数 |
| 5 | revert / hotfix / fix 提交数 | 滞后 | 非合并提交主题以 `Revert`、`hotfix`、`fix(` / `fix:` 开头 |

暂不计算（规格 §3.5 表）：冻结后缺陷数（followups 台账条目需先加类型标签）、CI 失败率（需 GitHub Actions 运行记录积累）、review Important 采纳率（SD2.3 自动 review 暂缓）、evals 通过率（SD3b 门控）。

## 3. 解读与已知局限

1. **立项 → 冻结呈双峰**：SX、WC、IR 跨夜，约 17–19 h；LG、WP、WS、SR 不到 1.5 h。后者是同一会话内「立项 → 实现 → 冻结」连续完成，WP 立项到冻结只隔 4 分钟（立项提交 4682305 同时做了目录治理）。这类数字反映会话节奏，不反映规格质量。1.1 版设阈值前需要更多样本，或改看「每个任务提交的平均间隔」。
2. **IR 没有首任务样本**：IR 系列提交主题写作 `IR7.1/IR7.2 ...`，没有方括号，按口径不计。口径不放宽，避免把「IR7」这类正文提及误认为任务提交；验收要求覆盖的 SR、WS、WP、WC、LG 五个系列都有样本。
3. **修复轮数按行匹配**：SD 系列早期提交在 `Fix-Rounds` 与 `Co-authored-by` 之间留了空行，`git interpret-trailers` 不认作 trailer，所以脚本按行匹配。此后的提交把 `Fix-Rounds` 紧贴在 trailer 块内。目前样本全是文档与配置类任务，0 轮不代表编码任务的水平。
4. **QA 周转需要先有执行记录**：qa-tester 跑过一轮并逐行写回进度文件之后，这个指标才有数据。SD4.3 的定时 QA 回归是主要数据来源。
5. **提交时间而非作者时间**：rebase 会改提交者时间。D1 之后合入走 merge commit，不 rebase，口径稳定。
